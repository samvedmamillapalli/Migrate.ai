# AWS Service Audit — Migration Oracle

Factual reference. Generated by reading `infra/sam/template.yaml`,
`infra/stepfunctions/migration_workflow.asl.json`, and every file under
`backend/app/` that imports `boto3` or touches an AWS client, directly or
transitively. Every claim below is anchored to a file path and, where
relevant, a line-level code reference. Anything not found in the code is
marked NOT PRESENT rather than inferred.

Two credential/permission boundaries exist in this system and are easy to
conflate:

1. **The SAM-deployed Lambda fleet** — eight Lambda functions, each with its
   own IAM role from `infra/sam/template.yaml`. This is the only place
   per-function least-privilege scoping actually applies.
2. **The FastAPI control plane** (`backend/app/main.py`, run via
   `backend/_run_api.py` or in Lambda-less local dev) — uses its own AWS
   credentials (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` or profile/role,
   see `app/aws/config.py`), entirely outside the SAM template's IAM
   policies. It calls Bedrock, Secrets Manager, S3, STS, and Step Functions
   directly for interactive (non-workflow) requests.

Every section below states which boundary applies.

## 1. AWS Step Functions

### Where it is declared

`infra/sam/template.yaml`, resource `MigrationStateMachine`:

```yaml
MigrationStateMachine:
  Type: AWS::Serverless::StateMachine
  Properties:
    Name: !Sub "${ProjectName}-migration-workflow"
    Type: STANDARD
    DefinitionUri: ../stepfunctions/migration_workflow.asl.json
    DefinitionSubstitutions:
      DiscoverSchemaFunctionArn: !GetAtt DiscoverSchemaFunction.Arn
      ProvisionShadowClusterFunctionArn: !GetAtt ProvisionShadowClusterFunction.Arn
      LoadSchemaFunctionArn: !GetAtt LoadSchemaFunction.Arn
      ExecuteMigrationFunctionArn: !GetAtt ExecuteMigrationFunction.Arn
      CollectMetricsFunctionArn: !GetAtt CollectMetricsFunction.Arn
      PersistResultsFunctionArn: !GetAtt PersistResultsFunction.Arn
      CleanupFunctionArn: !GetAtt CleanupFunction.Arn
    Policies:
      - LambdaInvokePolicy: { FunctionName: !Ref DiscoverSchemaFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref ProvisionShadowClusterFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref LoadSchemaFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref ExecuteMigrationFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref CollectMetricsFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref PersistResultsFunction }
      - LambdaInvokePolicy: { FunctionName: !Ref CleanupFunction }
```

The actual state definitions live in the separate file
`infra/stepfunctions/migration_workflow.asl.json` (referenced via
`DefinitionUri`, not inlined). States: `DiscoverSchema`,
`ProvisionShadowCluster`, `LoadSchema`, `ExecuteMigration`,
`CollectMetrics`, `PersistResults`, `MarkSucceeded`, `MarkFailed`,
`Cleanup`, `ChooseOutcome`, `WorkflowSucceeded`, `WorkflowFailed`,
`CleanupFailed`.

`app/aws/workflow/definition.py` loads the **same file** (path computed as
`Path(__file__).resolve().parents[4] / "infra" / "stepfunctions" /
"migration_workflow.asl.json"`, `_ASL_PATH`) at runtime to render Lambda ARN
substitutions and run structural validation. This is not a second
definition — it is the single source file read twice for two purposes
(deploy vs. runtime validation).

### Where it is called from

- `backend/app/aws/workflow/client.py`:
  - `_start_execution_sync()` → `client.start_execution(stateMachineArn=..., name=..., input=...)`
  - `_describe_execution_sync()` → `factory.stepfunctions().describe_execution(executionArn=...)`
  - `_stop_execution_sync()` → `client.stop_execution(executionArn=..., error=..., cause=...)`
  - `_validate_definition_sync()` → `factory.stepfunctions().validate_state_machine_definition(definition=..., type="STANDARD")`
- `backend/app/services/workflow_orchestration_service.py`:
  - `WorkflowOrchestrationService.start_for_run()` (line ~152) calls `start_workflow_execution()`
  - `WorkflowOrchestrationService.sync_status()` (line ~207) calls `describe_workflow_execution()`
  - `WorkflowOrchestrationService.abort_for_run()` (line ~285) calls `stop_workflow_execution()`
- `backend/scripts/verify_phase8_full.py` and `backend/scripts/validate_migration_workflow.py` call `validate_workflow_definition()`.

**`validate_workflow_definition()` is not called from any API route or
Lambda handler** — only from the two verification scripts above. It never
runs during normal request handling.

All four calls (`start_execution`, `describe_execution`, `stop_execution`,
`validate_state_machine_definition`) originate from the **FastAPI control
plane's own AWS credentials**, not from any Lambda's IAM role — no Lambda
function ever calls the Step Functions API itself.

### What it actually does in the pipeline

`WorkflowOrchestrationService.start_for_run()` builds a `WorkflowStartInput`
(`run_id`, `connection_secret_arn`, `artifacts_bucket`) and calls
`start_execution` with `name=run_id` (the run's UUID as string), making the
execution name deterministic and start idempotent (`ExecutionAlreadyExists`
is caught and treated as "already running, attach to it"). Step Functions
then invokes the seven Lambdas in ASL order, threading `run_id`,
`connection_secret_arn`, and `artifacts_bucket` through `$.run_id`,
`$.connection_secret_arn`, `$.artifacts_bucket`, plus each prior step's
output under `$.step_results.<state_name>`. `sync_status`/`describe_execution`
reads back `status`/`error`/`cause`/`startDate`/`stopDate` and writes them
onto the `MigrationRun.workflow_status`/`workflow_started_at`/
`workflow_finished_at`/`explainability["workflow"]` columns.

### Exact configuration values

- `Type: STANDARD` (not Express)
- `TimeoutSeconds: 3600` (whole-execution ceiling, from the ASL root)
- Per-state `TimeoutSeconds`: DiscoverSchema 300, ProvisionShadowCluster 900,
  LoadSchema 600, ExecuteMigration 900, CollectMetrics 300, PersistResults
  120, Cleanup 600
- Per-state `Retry` (`ErrorEquals: [Lambda.ServiceException,
  Lambda.AWSLambdaException, Lambda.SdkClientException,
  Lambda.TooManyRequestsException, States.Timeout]` on all seven):
  | State | IntervalSeconds | BackoffRate | MaxAttempts |
  |---|---|---|---|
  | DiscoverSchema | 2 | 2 | 3 |
  | ProvisionShadowCluster | 5 | 2 | 3 |
  | LoadSchema | 3 | 2 | 3 |
  | ExecuteMigration | 5 | 2 | 2 |
  | CollectMetrics | 2 | 2 | 3 |
  | PersistResults | 2 | 2 | 3 |
  | Cleanup | 5 | 2 | 4 |
- Every non-Cleanup task's `Catch` is `ErrorEquals: ["States.ALL"]` →
  `ResultPath: $.error` → `Next: MarkFailed`.
- `MarkSucceeded`/`MarkFailed` are `Pass` states writing
  `$.outcome.workflow_failed` (`false`/`true`), both `Next: Cleanup`.
- `Cleanup`'s own `Catch` → `ResultPath: $.cleanup_error` → `Next:
  CleanupFailed` (a terminal `Fail` state, distinct from `WorkflowFailed`).
- `ChooseOutcome` is a `Choice` state: `$.outcome.workflow_failed ==
  true` → `WorkflowFailed`, `Default` → `WorkflowSucceeded`.
- Env var read by the control plane: `MIGRATION_WORKFLOW_ARN`
  (`AwsSettings.migration_workflow_arn`, no default — required to start
  workflows).

### IAM permissions

The state machine's execution role (auto-generated by SAM from the
`Policies:` block above) is granted exactly seven `LambdaInvokePolicy`
grants, one per workflow Lambda — it cannot invoke `ShadowSweeperFunction`
or anything else.

No Lambda function's own IAM policy grants any `states:*` action — none of
the eight functions can call `StartExecution`, `DescribeExecution`, or
`StopExecution`. Only the FastAPI control plane's own (SAM-external)
credentials can do that.

### What breaks without it

If `MigrationWorkflowArn` is unset or the state machine doesn't exist,
`WorkflowOrchestrationService.start_for_run()` raises
`AwsConfigurationError("MIGRATION_WORKFLOW_ARN is required to start
workflows")` before any AWS call — the run stays in whatever status it was
(`awaiting_approval` or similar) and no shadow cluster is ever provisioned.
There is a compensating path: `POST /runs/{id}/verify-local` (the
"local/mock verify path", `local_verify_available` in `/health`) runs the
same lifecycle via `ShadowClusterOrchestrator` in-process, without Step
Functions, Lambda, or any of the durability guarantees below — no retry, no
guaranteed cleanup across a process crash, single Python `try/finally`.

### One real snippet

`infra/stepfunctions/migration_workflow.asl.json` — the guaranteed-cleanup
pattern:

```json
"MarkFailed": {
  "Type": "Pass",
  "Comment": "Preserve error context, then always run Cleanup.",
  "Result": { "workflow_failed": true },
  "ResultPath": "$.outcome",
  "Next": "Cleanup"
},
"Cleanup": {
  "Type": "Task",
  "Resource": "${CleanupFunctionArn}",
  "Catch": [{ "ErrorEquals": ["States.ALL"], "ResultPath": "$.cleanup_error", "Next": "CleanupFailed" }],
  "Next": "ChooseOutcome"
}
```

| `ProvisionShadowClusterFunction` | `${ProjectName}-provision-shadow-cluster` | `app.lambdas.handlers.provision_shadow.handler` | 900 | 1024 |
| `LoadSchemaFunction` | `${ProjectName}-load-schema` | `app.lambdas.handlers.load_schema.handler` | 600 | 1024 |
| `ExecuteMigrationFunction` | `${ProjectName}-execute-migration` | `app.lambdas.handlers.execute_migration.handler` | 900 | 1024 |

### Where it is called from

Each handler is a plain `def handler(event, context=None) -> dict` in
`backend/app/lambdas/handlers/*.py`. None of them call any AWS SDK method
named `lambda:*` (i.e. no function invokes another function over the
network). `AwsClientFactory.lambda_()` (`app/aws/clients.py:105`) — a cached
`boto3` `lambda` client — is defined but **never called anywhere in the
codebase** (confirmed by exhaustive grep; no `.lambda_()` call site exists).

Two non-network ways a handler runs outside the deployed Step Functions
path:
- `backend/app/services/workflow_orchestration_service.py:293-300`
  (`abort_for_run`) imports `HANDLERS["cleanup"]` from
  `app.lambdas` and calls it as a **plain in-process Python function call**
  (`HANDLERS["cleanup"]({"run_id": ..., "connection_secret_arn": ...})`),
  because `StopExecution` does not run the ASL `Cleanup` state. This is not
  a `lambda:Invoke` API call — it runs the handler's Python code inside the
  FastAPI process.
- `backend/app/lambdas/__init__.py`'s docstring calls out "or via the local
  runner" — `HANDLERS` (dict of the seven workflow handlers, keyed
  `"discover-schema"`, `"provision-shadow-cluster"`, `"load-schema"`,
  `"execute-migration"`, `"collect-metrics"`, `"persist-results"`,
  `"cleanup"`) exists specifically so a local runner script can call
  handlers directly without AWS Lambda at all.

### What it actually does in the pipeline

Each function receives the Step Functions state's `Parameters` block as
`event` (a plain dict — `run_id`, plus whatever prior `ResultPath`s the ASL
threads in), does its one job (see the per-service sections below for what
each touches), and returns a JSON-serializable dict that becomes
`$.step_results.<StateName>` for the next state.

`CCLOUD_API_KEY_SECRET_ARN=${CCloudApiKeySecretArn}`,
`USER_DATABASE_SECRET_PREFIX=${UserDatabaseSecretPrefix}`,
`BEDROCK_PREDICTION_MODEL_ID=${BedrockPredictionModelId}` (parameter default

`BEDROCK_RECOMMENDATION_MODEL_ID=${BedrockRecommendationModelId}` (same

`run_async()` (`app/lambdas/runtime.py:142`) sets

### IAM permissions

See the per-service IAM subsections below (S3, Secrets Manager, CloudWatch,
Bedrock) — each function's `Policies:` block in the template is the
authoritative source. Summarized allow/deny matrix:

| Function | S3 | Secrets Manager | Bedrock | CloudWatch metrics | Logs |
|---|---|---|---|---|---|
| DiscoverSchemaFunction | ✅ | ✅ (read `${UserDatabaseSecretPrefix}*`, `migration-oracle/connections*`) | ❌ | ✅ | ✅ |
| ProvisionShadowClusterFunction | ✅ | ✅ (read/write/tag `migration-oracle/shadow*`, `${UserDatabaseSecretPrefix}*`, optionally `CCloudApiKeySecretArn`) | ❌ | ✅ | ✅ |
| LoadSchemaFunction | ✅ | ✅ (read-only `migration-oracle/shadow*`) | ❌ | ✅ | ✅ |
| ExecuteMigrationFunction | ✅ | ✅ (read-only `migration-oracle/shadow*`) | ❌ | ✅ | ✅ |
| CollectMetricsFunction | ✅ | ✅ (read-only `migration-oracle/shadow*`) | ❌ | ✅ | ✅ |
| PersistResultsFunction | ✅ | ❌ (no Secrets Manager statement at all) | ✅ (`bedrock:InvokeModel`, `InvokeModelWithResponseStream` on `foundation-model/*` and `inference-profile/*`) | ✅ | ✅ |
| CleanupFunction | ✅ | ✅ (read/describe/**delete** `migration-oracle/shadow*`) | ❌ | ✅ | ✅ |
| ShadowSweeperFunction | ❌ (no S3 statement) | ✅ (read-only, either `CCloudApiKeySecretArn` if set or `migration-oracle/*` wildcard) | ❌ | ✅ | ✅ |

`PersistResultsFunction` is the only function with any `bedrock:*`
permission. `CleanupFunction` is the only function with
`secretsmanager:DeleteSecret`. `ProvisionShadowClusterFunction` is the only
function with `secretsmanager:CreateSecret`/`PutSecretValue`/`TagResource`.
This scoping applies **only to workflow executions that actually go through
Step Functions** — see §8 (Bedrock) for why this is not the whole truth
about who can reach Bedrock.

### What breaks without it

If a function fails to deploy or its code raises before returning, the ASL
`Retry` block retries per the table in §1, then `Catch` routes to
`MarkFailed → Cleanup`. Cleanup itself is idempotent (checks
`ShadowClusterStatus`, tolerates "no shadow row") so a failure in any single
step still results in an attempted teardown of whatever was provisioned so
far.

## 3. AWS Secrets Manager

### Where it is declared

No standalone `AWS::SecretsManager::Secret` resource exists in
`infra/sam/template.yaml` — every secret is created **at runtime** by
`ProvisionShadowClusterFunction` (shadow DB credentials) or by the FastAPI
control plane (`_store_connection_url` in `app/api/routes/runs.py`, customer
connection URLs), never declared as infrastructure. Only the IAM policy
statements referencing `secretsmanager:*` actions are declared in the
template (see §2's table and the per-function blocks quoted below).

`DiscoverSchemaFunction`:
```yaml
- Effect: Allow
  Action: [secretsmanager:GetSecretValue, secretsmanager:DescribeSecret]
  Resource:
    - !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:${UserDatabaseSecretPrefix}*"
    - !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:migration-oracle/connections*"
```

`ProvisionShadowClusterFunction`:
```yaml
- Effect: Allow
  Action:
    - secretsmanager:GetSecretValue
    - secretsmanager:DescribeSecret
    - secretsmanager:CreateSecret
    - secretsmanager:PutSecretValue
    - secretsmanager:UpdateSecret
    - secretsmanager:TagResource
  Resource:
    - !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:migration-oracle/shadow*"
    - !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:${UserDatabaseSecretPrefix}*"
    - !If [HasCCloudSecretArn, !Ref CCloudApiKeySecretArn, !Ref AWS::NoValue]
```

`CleanupFunction` (only function that can delete):
```yaml
- Effect: Allow
  Action: [secretsmanager:GetSecretValue, secretsmanager:DescribeSecret, secretsmanager:DeleteSecret]
  Resource: !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:migration-oracle/shadow*"
```

`LoadSchemaFunction`, `ExecuteMigrationFunction`, `CollectMetricsFunction`:
identical read-only block, `Resource: migration-oracle/shadow*` only.

`ShadowSweeperFunction`:
```yaml
- Effect: Allow
  Action: [secretsmanager:GetSecretValue, secretsmanager:DescribeSecret]
  Resource: !If
    - HasCCloudSecretArn
    - [!Ref CCloudApiKeySecretArn]
    - [!Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:migration-oracle/*"]
```

### Where it is called from

`backend/app/aws/secrets_service.py`, class `SecretsService` (wraps
`factory.secretsmanager()`):
- `_describe()` → `client.describe_secret(SecretId=...)`
- `_get_secret_string_sync()` → `client.get_secret_value(SecretId=...)`
- `put_string_sync()` → `client.put_secret_value(SecretId=arn, SecretString=...)` (update path) or `client.create_secret(Name=..., SecretString=..., [Description=...])` (create path)
- `delete()` → `client.delete_secret(SecretId=..., ForceDeleteWithoutRecovery=True)`

`backend/app/lambdas/secrets.py`, class `AwsSecretStore` — thin async
wrapper around the above four operations (`get_json`, `get_string`,
`put_string`, `put_json`, `delete`), used by every Lambda handler via
`runtime.secrets`.

Call sites by handler:
- `discover_schema.py:74` — `runtime.secrets.get_json(secret_arn)` (customer connection)
- `provision_shadow.py:126,156` — `runtime.secrets.get_string(shadow_secret_name(run_id))` (resume path) and `runtime.secrets.put_string(shadow_secret_name(run_id), connection_url)` (write shadow credential)
- `load_schema.py:81` — `runtime.secrets.get_string(str(shadow_secret_arn))`
- `execute_migration.py:61` — `runtime.secrets.get_string(str(shadow_secret_arn))`
- `cleanup.py:152` (`_delete_secret`) — `runtime.secrets.delete(secret_id)`
- `collect_metrics.py` — **no Secrets Manager call** (pure data transform on the prior step's event payload)
- `persist_results.py` — **no Secrets Manager call**

Control-plane (non-Lambda) call site:
- `backend/app/api/routes/runs.py:658` `_store_connection_url()` — calls
  `get_runtime().secrets.put_json(name, {"database_url": database_url})`
  with `name = f"migration-oracle/connections/{run_id}"`. Falls back to an
  in-process dict (`request.app.state._demo_secrets`) only when
  `environment` is `development`/`dev`/`local`/`test`; refuses the fallback
  and re-raises otherwise.
- `backend/app/api/routes/runs.py:690` `_load_connection()` — reads back via
  `runtime.secrets.get_json(secret_arn)`, checking the in-process demo dict
  first.

`SecretsService.store_customer_connection()`
(`app/aws/secrets_service.py:261`) is defined but has **zero call sites**
anywhere in `backend/` — dead code. The actual customer-secret write path is
`_store_connection_url` above, which uses the lower-level `put_json`
directly, not this method.

### What it actually does in the pipeline

Two distinct secret families exist, both stored under the `migration-oracle/`
namespace by naming convention (not enforced by the SDK, only by the IAM
resource patterns above):
- `migration-oracle/connections/{run_id}` — the customer's read-only
  database URL, written once by the control plane when a run is created or
  a database is attached, read by `DiscoverSchemaFunction`.
- `migration-oracle/shadow/{run_id}` — the freshly-provisioned shadow
  cluster's own connection string, written by `ProvisionShadowClusterFunction`
  once the CockroachDB Cloud shadow cluster is ready, read by
  `LoadSchemaFunction` and `ExecuteMigrationFunction`, deleted by
  `CleanupFunction`. This is the credential that never travels through Step
  Functions execution state — only its ARN/name does (`shadow_secret_arn` in
  the event payload).

### Exact configuration values

- `UserDatabaseSecretPrefix` parameter, default `migration-oracle/connections`
  (`AwsSettings.user_database_secret_prefix`, same default in
  `app/aws/config.py`)
- Shadow secret name pattern (both `app/aws/secrets_service.py:62`
  `shadow_secret_name()` and `app/lambdas/helpers.py:112-113`
  `shadow_secret_name()` — two independent functions with identical output):
  `f"migration-oracle/shadow/{run_id}"`
- In-process cache TTL: `cache_ttl_seconds: float = 300.0` default on
  `SecretsService.__init__`, sourced from
  `AwsSettings.secrets_cache_ttl_seconds` (default `300.0`, env
  `AWS_SECRETS_CACHE_TTL_SECONDS`, bounded `0.0`–`3600.0`)
- `delete()` always passes `ForceDeleteWithoutRecovery=True` (no 7/30-day
  recovery window — immediate delete)

### IAM permissions

See declaration table above. Precisely: only `ProvisionShadowClusterFunction`
can `CreateSecret`/`PutSecretValue`/`TagResource`; only `CleanupFunction` can
`DeleteSecret`; `DiscoverSchemaFunction` can read the customer-connection
prefix but not the shadow prefix; `LoadSchema`/`ExecuteMigration`/
`CollectMetrics` can read only the shadow prefix.

This scoping is real **only for the Step-Functions-triggered execution
path**. The FastAPI control plane's `_store_connection_url`/`_load_connection`
calls use the control plane's own AWS credentials (outside this template
entirely) to read and write the `migration-oracle/connections/*` secrets —
those calls are not constrained by `DiscoverSchemaFunction`'s IAM policy at
all, because they don't run as that Lambda.

### What breaks without it

If `ProvisionShadowClusterFunction` cannot write the shadow secret,
`provision_shadow.py` raises before returning, caught by `LambdaHandlerError`
wrapping (redacting any `Bearer ` token text first), which surfaces as a
Step Functions `Catch` → `MarkFailed` → `Cleanup`. If `LoadSchema` or
`ExecuteMigration` cannot read the shadow secret (e.g. it was already
deleted by a concurrent Cleanup), `runtime.secrets.get_string` raises
`LambdaHandlerError` inside `AwsSecretStore.get_string`, same failure path.
No component silently proceeds without the credential.

### One real snippet

`backend/app/lambdas/handlers/provision_shadow.py:156-159`:

```python
secret_arn = await runtime.secrets.put_string(
    shadow_secret_name(run_id),
    connection_url,
)
```

## 4. Amazon S3

### Where it is declared

`infra/sam/template.yaml`, resource `RunArtifactsBucket`:

```yaml
RunArtifactsBucket:
  Type: AWS::S3::Bucket
  Properties:
    BucketName: !If
      - HasBucketName
      - !Ref ArtifactsBucketName
      - !Sub "${ProjectName}-artifacts-${AWS::AccountId}"
    BucketEncryption:
      ServerSideEncryptionConfiguration:
        - ServerSideEncryptionByDefault: { SSEAlgorithm: AES256 }
    PublicAccessBlockConfiguration:
      BlockPublicAcls: true
      BlockPublicPolicy: true
      IgnorePublicAcls: true
      RestrictPublicBuckets: true
```

IAM statement granted to `DiscoverSchemaFunction`, `ProvisionShadowClusterFunction`,
`LoadSchemaFunction`, `ExecuteMigrationFunction`, `CollectMetricsFunction`,
`PersistResultsFunction`, `CleanupFunction` (all seven workflow functions,
identical block each time except Discover also gets `AbortMultipartUpload`):

```yaml
- Effect: Allow
  Action: [s3:PutObject, s3:GetObject, s3:ListBucket]  # Discover adds s3:AbortMultipartUpload
  Resource:
    - !Sub "arn:aws:s3:::${RunArtifactsBucket}"
    - !Sub "arn:aws:s3:::${RunArtifactsBucket}/*"
```

`ShadowSweeperFunction` has **no S3 statement at all**.

### Where it is called from

`backend/app/aws/artifacts.py`, class `ArtifactStore` (wraps `factory.s3()`):
- `_head()` → `client.head_object(Bucket=..., Key=...)` (existence/idempotency check)

`check_aws_connectivity(factory)` with the default `probe_configured_resources=False`,
so **this S3 health probe is defined but not exercised by the live `/health`
route** as currently wired.

### What it actually does in the pipeline

`DiscoverSchemaFunction` writes the discovered customer schema (table/column/
index/constraint shape, from Phase 6 discovery) to
`runs/{run_id}/schema_snapshot.json`. `PersistResultsFunction` writes the
final execution report (success, duration, storage growth, rollback flag,
error message) to `runs/{run_id}/execution_report.json`. Both are
write-then-forget from the Lambda's perspective — nothing in the current
codebase reads either object back via `get_json`/`get_bytes` (`ArtifactStore.get_bytes`/`get_json`
have no call sites either, beyond their own class definition and unit-test
usage patterns implied by their existence). The schema snapshot's
authoritative copy for downstream steps is the `MigrationRun.schema_snapshot`
JSONB column in CockroachDB, not the S3 object — S3 here is an artifact
trail, not an inter-step handoff mechanism.

### Exact configuration values

- Bucket name: parameter `ArtifactsBucketName` if set, else
  `!Sub "${ProjectName}-artifacts-${AWS::AccountId}"` → with default
  `ProjectName=migration-oracle`, e.g. `migration-oracle-artifacts-630434208625`
  (account id observed in a live `/health` response during this session)
- `BucketEncryption`: `AES256` (SSE-S3, not KMS)
- All four `PublicAccessBlockConfiguration` flags `true`
- Key convention (`ArtifactStore` static methods):
  `runs/{run_id}/schema_snapshot.json`,
  `runs/{run_id}/execution_report.json`,
  `runs/{run_id}/steps/{step_name}.json` (unused convention)
- Idempotency: uploads compute `hashlib.sha256(body).hexdigest()`, compare
  against the existing object's `x-amz-meta-migration-oracle-content-sha256`
  metadata key (`_CONTENT_HASH_METADATA_KEY`), skip the `put_object` call if
  unchanged
- Env var: `RUN_ARTIFACTS_BUCKET` (`AwsSettings.run_artifacts_bucket`, no
  default, required to construct `ArtifactStore.bucket`)

### IAM permissions

See table in §2. Six of seven S3-permissioned functions
(`ProvisionShadowCluster`, `LoadSchema`, `ExecuteMigration`, `CollectMetrics`,
`Cleanup` — five of the six, `Discover` and `PersistResults` are the two
that do use it) hold `s3:PutObject`/`GetObject`/`ListBucket` that their
current handler code never exercises.

### What breaks without it

If `RUN_ARTIFACTS_BUCKET` is unset, `ArtifactStore.bucket` raises
`AwsConfigurationError` the first time it's accessed — but both call sites
(`discover_schema.py`, `persist_results.py`) guard with `if runtime.artifacts
is not None` / `if not snapshot or runtime.artifacts is None: return None`,
so a missing bucket degrades to `schema_snapshot_uri: null` /
`execution_report_uri: null` in the handler's return payload rather than
failing the step. The authoritative data (schema snapshot, execution
result) still lands in CockroachDB via the repository/service layer
regardless of S3 outcome — S3 failure here is non-fatal by design.

Control-plane call site: `backend/app/aws/health.py` does not call

### What it actually does in the pipeline

Two purpose-built operational metrics (`CleanupFailed`, dimensioned by
`RunId` plus an undimensioned rollup; `OrphanedShadowClusters`, a gauge of
`report["orphan_candidates"]` count) feed the two alarms defined in
`ensure_standard_alarms()`. Four separate accuracy/retrieval metrics
(`PredictionScalarAccuracy`, `RecommendationSuccessRate`,
`RecommendationAcceptanceRate`, `RetrievalUsefulCount`) are published after
every graded run, sourced from `fetch_accuracy_metrics()` (a CockroachDB
query) — CloudWatch here is a downstream mirror of numbers whose source of
truth is the database, not the origin of them.

### Exact configuration values

- Namespace: `MigrationOracle` (`cloudwatch_namespace`, env
  `AWS_CLOUDWATCH_NAMESPACE`) — matches the IAM `Condition` exactly, so
  publishing to any other namespace would be denied.
- Log group naming (`CloudWatchObservability`):
  `primary_log_group` = `AWS_CLOUDWATCH_LOG_GROUP` or default
  `/migration-oracle/application`; `workflow_log_group()` =
  `/migration-oracle/workflow`; `lambda_log_group(suffix)` =
  `/migration-oracle/lambda/{AWS_LAMBDA_FUNCTION_PREFIX}-{suffix}`
- `cloudwatch_log_retention_days`: default `14`, bounded `1`–`3653`, env
  `AWS_CLOUDWATCH_LOG_RETENTION_DAYS`
- Alarm `migration-oracle-cleanup-failed`: metric `CleanupFailed`,
  `Statistic: Sum`, `ComparisonOperator: GreaterThanOrEqualToThreshold`,
  threshold default `1` (`AWS_ALARM_CLEANUP_FAILED_THRESHOLD`), period
  default `60`s (`AWS_ALARM_CLEANUP_FAILED_PERIOD_SECONDS`, min `60`),
  evaluation periods default `5` (`AWS_ALARM_CLEANUP_FAILED_EVALUATION_PERIODS`),
  `TreatMissingData: notBreaching`
- Alarm `migration-oracle-orphaned-shadow-clusters`: metric
  `OrphanedShadowClusters`, `Statistic: Maximum`, same comparison operator,
  threshold default `1`, period default `300`s, evaluation periods default
  `2`
- Both alarms created with `ActionsEnabled: False` — they can fire (go into
  `ALARM` state) but never notify anything (no SNS topic, no action ARN
  anywhere in the codebase)

### IAM permissions

`cloudwatch:PutMetricData` and `logs:CreateLogGroup`/`CreateLogStream`/
`PutLogEvents` are granted to all eight functions, scoped to the
`MigrationOracle` namespace (metrics) and `/aws/lambda/${ProjectName}-*`
(log streams — standard Lambda-managed log groups, distinct from the
`/migration-oracle/*` custom log group names `CloudWatchObservability`
computes, which no function is actually permissioned to create — see §7.

### What breaks without it

`record_cleanup_failed`/`record_orphaned_shadow_clusters`/
`publish_metrics_to_cloudwatch` are all wrapped in bare `try/except
Exception` that logs a warning and continues — a CloudWatch outage or
missing permission never fails a workflow step or blocks grading. The
`ALARM_CLEANUP_FAILED`/`ALARM_ORPHANED_CLUSTERS` alarms, since
`ActionsEnabled: False`, never notify anyone even when they do fire — there
is no compensating notification path (no SNS, no email, no Slack webhook)
anywhere in this codebase. An operator would have to open the CloudWatch
console to see them.

## 6. Amazon EventBridge

### Where it is declared

Not a standalone `AWS::Events::Rule` resource — synthesized implicitly by
the SAM `Events:` block on `ShadowSweeperFunction`:

```yaml
ShadowSweeperFunction:
  Type: AWS::Serverless::Function
  Properties:
    FunctionName: !Sub "${ProjectName}-shadow-sweeper"
    ...
    Events:
      Schedule:
        Type: Schedule
        Properties:
          Schedule: !Ref SweeperScheduleExpression
          Description: Reap orphaned CockroachDB Cloud shadow clusters
```

`SweeperScheduleExpression` parameter, default `rate(15 minutes)`
(`infra/sam/template.yaml` Parameters block).

### Where it is called from

Not called from application code at all — EventBridge is the trigger, not
something the application invokes. The application only reacts to the
invocation: `backend/app/lambdas/handlers/sweep_orphans.py`'s `handler()`
receives the EventBridge-delivered `event` (or `None`, defaulted to `{}`)
and passes `require_run=False` to `handler_correlation` because "EventBridge
schedule has no run_id" (source comment, line 19).

### What it actually does in the pipeline

Fires `ShadowSweeperFunction` every 15 minutes regardless of whether any
Step Functions execution is running, succeeded, or failed. The sweeper
reads `shadow_clusters` rows from CockroachDB whose `expires_at` has passed
(`ShadowClusterService.list_expired_active`) and destroys them via the
shadow provider, and separately asks the provider directly for all
clusters tagged with `SHADOW_APP_TAG` older than
`SHADOW_MAX_LIFETIME_MINUTES`, destroying any with no matching DB row (the
"process died mid-lifecycle, DB row never got created or was lost" case).

### Exact configuration values

- `SweeperScheduleExpression`: `rate(15 minutes)` (parameter default, can be
  overridden at deploy time)
- `SHADOW_MAX_LIFETIME_MINUTES`: consumed as
  `runtime.settings.shadow_max_lifetime_minutes` inside the handler — not
  an AWS-side value, a `Settings` field (default documented as `30` in
  `docs/PHASE_7_SHADOW_CLUSTERS.md`; not re-verified against
  `app/config.py` in this audit)

### IAM permissions

`ShadowSweeperFunction` holds no S3 permission, read-only Secrets Manager
(scoped to `CCloudApiKeySecretArn` if provided, else `migration-oracle/*`),
and the same CloudWatch metrics/logs grants as every other function. SAM
auto-attaches whatever permission the `Schedule` event source needs for
EventBridge to invoke the function (a resource-based Lambda permission, not
part of the `Policies:` IAM-role block shown above — not independently
verified in this audit beyond noting SAM handles it as standard behavior
for the `Schedule` event type).

### What breaks without it

If the schedule were removed or failed to fire, orphaned shadow clusters
(from a crashed control plane, a Step Functions execution that hit the
overall 3600s `TimeoutSeconds` ceiling, or an ASL `Cleanup` state that
itself failed and landed in `CleanupFailed`) would never be reclaimed
automatically. No other component in this codebase performs this reaping —
the sweeper is explicitly the only backstop (see `sweeper.py`'s module
docstring: "never leak orphaned clusters when a process dies
mid-lifecycle").

### One real snippet

`infra/sam/template.yaml`:

```yaml
      Events:
        Schedule:
          Type: Schedule
          Properties:
            Schedule: !Ref SweeperScheduleExpression
            Description: Reap orphaned CockroachDB Cloud shadow clusters
```

## 7. Amazon Bedrock

### Where it is declared

No `AWS::Bedrock::*` resource exists (Bedrock foundation models are not
CloudFormation-managed resources). Only the IAM policy statement matters,
and it is granted to **exactly one** function, `PersistResultsFunction`:

```yaml
- Effect: Allow
  Action: [bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream]
  Resource:
    - !Sub "arn:aws:bedrock:us-east-1::foundation-model/*"
    - !Sub "arn:aws:bedrock:us-east-1:${AWS::AccountId}:inference-profile/*"
```

No other function's `Policies:` block contains any `bedrock:*` action.

### Where it is called from

Two separate client classes, two separate Bedrock Runtime API operations:

- `backend/app/prediction/bedrock_client.py`, class `AwsBedrockClient` —
  `self._client.converse(modelId=..., system=[...], messages=[...],
  inferenceConfig={...})` (the **Converse API**, not `InvokeModel`), used
  for prediction/recommendation/grading-prose text generation.
  `generate_json()` (line 162) is the sole call site of `.converse()`.
- `backend/app/memory/embedding_client.py`, class `AwsTitanEmbeddingClient`
  — `self._client.invoke_model(modelId=..., contentType="application/json",
  accept="application/json", body=json.dumps({"inputText":...,
  "dimensions":...,"normalize":True}))` (the classic **InvokeModel API**),
  used for Titan text embeddings. `embed()` (line 91) is the sole call
  site.

Both classes construct their own `bedrock-runtime` boto3 client internally
(`session.client("bedrock-runtime", region_name=settings.bedrock_region,
config=...)`) rather than going through `AwsClientFactory` — `bedrock-runtime`
is not in `AwsClientFactory._KNOWN_SERVICES` (`{"sts", "stepfunctions",
"lambda", "s3", "secretsmanager", "logs", "cloudwatch"}`) at all.

Construction call sites (who actually builds these clients — this is where
the "only `PersistResultsFunction` can reach Bedrock" IAM claim needs
qualifying):
- `backend/app/lambdas/handlers/persist_results.py:67,87`
  (`_build_grading_pipeline`) — inside the Lambda fleet, exactly as the IAM
  table implies.
- `backend/app/dependencies.py:183,211` — FastAPI dependency-injection
  providers, used directly by interactive API routes (e.g. `POST
  /runs/{id}/predict`) running on the **control plane**, not as
  `PersistResultsFunction`. These calls are governed by the control plane's
  own AWS credentials, entirely outside this template's IAM scoping.
- `backend/app/memory/open_source_corpus.py:282` — constructs
  `AwsTitanEmbeddingClient` directly for corpus-seeding, also control-plane
  code, also outside SAM's IAM boundary.

So the true statement is: **within the Step-Functions-orchestrated
pipeline**, only `PersistResultsFunction` can reach Bedrock. The FastAPI
control plane can reach Bedrock from several other places using a
completely different, broader credential.

### What it actually does in the pipeline

`PersistResultsFunction` uses Bedrock for **grading prose** only (per
`_build_grading_pipeline`'s `GradingPipelineService(bedrock_client=...,
prose_model_id=...)`) and for the Titan embedding written alongside the
graded memory (`MemoryWriteService(embedding_client=...)`). The primary
prediction/recommendation Bedrock calls (the ones a user actually watches
happen when they click "Run prediction" in the UI) happen synchronously in
the control plane via `app/dependencies.py`, **before** any Step Functions
execution starts — Bedrock prediction is explicitly not a workflow state
(confirmed by its absence from the ASL's `States` object; predict/approve
are API-side gates, per the ASL's own top-level `"Comment"` field).

### Exact configuration values

- `BedrockPredictionModelId` parameter default:
  `us.anthropic.claude-haiku-4-5-20251001-v1:0`
- `BedrockRecommendationModelId` parameter default:
  `us.anthropic.claude-haiku-4-5-20251001-v1:0`
- `BedrockEmbeddingModelId` parameter default: `amazon.titan-embed-text-v2:0`
  (also the field default in `AwsSettings.bedrock_embedding_model_id`,
  additionally re-defaulted by a `field_validator` if empty/whitespace)
- `BEDROCK_REGION=us-east-1` (hardcoded in `Globals.Function.Environment`,
  independent of `AWS_DEFAULT_REGION`)
- `AwsBedrockClient`: `inferenceConfig={"temperature": 0.0, "maxTokens":
  4096}` (fixed, not configurable via settings)
- `AwsBedrockClient`'s bedrock-runtime client: `read_timeout =
  max(120.0, settings.read_timeout_seconds)` (generic AWS read timeout
  default `10.0`s, so effectively always `120.0`s for this client),
  `retries={"max_attempts": settings.max_attempts, "mode": "standard"}`
  (`max_attempts` default `3`)
- `AwsTitanEmbeddingClient`'s client: `read_timeout = max(60.0,
  settings.read_timeout_seconds)` (effectively `60.0`s)
- Titan request body: `{"dimensions": EMBEDDING_DIMENSIONS, "normalize":
  True}` — exact numeric value of `EMBEDDING_DIMENSIONS`
  (`app/memory/constants.py`) not re-verified in this audit; the code
  asserts the returned vector length must equal it or raises
  `EmbeddingInvocationError`.
- Inference-profile fallback: if a bare `anthropic.*` model id is rejected,
  `_inference_profile_candidates()` retries with a region-prefixed profile
  id (`us.`/`eu.`/`apac.` + model id), inferred from
  `settings.bedrock_region`'s leading characters.

### IAM permissions

Only `PersistResultsFunction` — see declaration block above. All seven
other functions (including the sweeper) have zero `bedrock:*` grants and
would receive `AccessDeniedException` if they somehow tried to call
Bedrock.

### What breaks without it

`AwsBedrockClient.__init__` raises `AwsConfigurationError` immediately if
`BEDROCK_PREDICTION_MODEL_ID` is unset. `generate_json()` distinguishes
access errors (`AccessDeniedException`,
`UnrecognizedClientException`,`ResourceNotFoundException`,
`ValidationException` with access-related message text) from generic
invocation errors, raising `BedrockAccessError` (with an actionable message
pointing at the Bedrock console) vs. `BedrockInvocationError`. Inside

silently fall back to `MockBedrockClient` outside `development`/`dev`/

`production` deploy, a Bedrock failure here raises and fails the
`PersistResults` state (caught by ASL `Retry`/`Catch` like any other step
failure). There is no compensating "grade without prose" path for a real
deployed environment — grading's scalar/deterministic parts (duration,
storage, rollback bands) do not depend on Bedrock, but the prose narrative
and the memory embedding do.

## 8. IAM

### Where it is declared

No explicit `AWS::IAM::Role` or `AWS::IAM::Policy` resource exists in
`infra/sam/template.yaml` — every function's execution role is
**auto-generated by the SAM transform** from that function's inline
`Policies:` list (a sequence of policy-document fragments, quoted verbatim
throughout this document under each service's IAM section) plus SAM's own
default Lambda-basic-execution policy. `MigrationStateMachine`'s execution
role is likewise auto-generated from its `Policies:` list (the seven
`LambdaInvokePolicy` grants in §1).

### Where it is called from

No file in `backend/app/` imports or calls the `iam` boto3 client —
confirmed by exhaustive grep of `AwsClientFactory._KNOWN_SERVICES` (`{sts,
stepfunctions, lambda, s3, secretsmanager, logs, cloudwatch}`, no `iam`
entry) and by grepping the whole `backend/` tree for `"iam"` as a service
name. IAM in this project is entirely declarative infrastructure, never an
SDK call at runtime.

### What it actually does in the pipeline

Defines eight distinct trust/permission boundaries (one per Lambda) plus
one for the state machine, enforced by AWS at every API call each principal
makes — this is the mechanism behind every "only X can do Y" claim made
throughout this document.

### Exact configuration values

`Policies:` blocks use `Version: "2012-10-17"` throughout (the only IAM
policy-language version used). `Capabilities` required at deploy time
(from `deploy.ps1`): `CAPABILITY_IAM CAPABILITY_NAMED_IAM` (the stack
creates named/unnamed IAM identities, requiring explicit operator
acknowledgment).

### IAM permissions

See the consolidated table in §2 and each service's own IAM subsection —
this section exists to state plainly that IAM itself has no separate
"permissions to use IAM" story here; SAM's `Policies:` sugar is the whole
mechanism.

### What breaks without it

Not applicable in the failure-mode sense the other sections use — IAM
misconfiguration doesn't "break a step," it silently changes what a
function *can* do. A too-broad policy here would be the actual security
failure mode; a too-narrow one produces the `AccessDeniedException`
handling already covered per-service above (e.g. `BedrockAccessError` if
`PersistResultsFunction`'s policy were ever narrowed further).

### One real snippet

`infra/sam/template.yaml` — the narrowest single-purpose grant in the
template, illustrating the least-privilege pattern used throughout:

```yaml
CleanupFunction:
  ...
  Policies:
    - Version: "2012-10-17"
      Statement:
        - Effect: Allow
          Action:
            - secretsmanager:GetSecretValue
            - secretsmanager:DescribeSecret
            - secretsmanager:DeleteSecret
          Resource:
            - !Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:migration-oracle/shadow*"
```

| 2 | `ProvisionShadowCluster` | `provision-shadow-cluster` | Secrets Manager (put shadow secret; get, only on resume), CloudWatch Logs | `MigrationRun.schema_snapshot` from CockroachDB; CockroachDB Cloud REST API (via the shadow provider, not an AWS service) to create the cluster | `ShadowCluster` row (CockroachDB) via `ShadowClusterService`; secret `migration-oracle/shadow/{run_id}` |
| 3 | `LoadSchema` | `load-schema` | Secrets Manager (get shadow secret), CloudWatch Logs | Secret `migration-oracle/shadow/{run_id}`; `MigrationRun.schema_snapshot` | Shadow cluster's own schema (via direct SQL, not AWS); `ShadowCluster.stage_timings.seed_ms` in CockroachDB |
| 4 | `ExecuteMigration` | `execute-migration` | Secrets Manager (get shadow secret), CloudWatch Logs | Secret `migration-oracle/shadow/{run_id}`; `MigrationRun.migration_sql` | Shadow cluster's data (via direct SQL); `ShadowCluster.stage_timings.migrate_ms`, `.schema_snapshot_before/after`, `.row_sample_before/after` in CockroachDB |
| 5 | `CollectMetrics` | `collect-metrics` | **None** — pure in-memory transform | `event.execute_migration` (or `event.metrics`) from the ASL step-results payload | Nothing persisted — returns a normalized dict for the next state |
| 6 | `PersistResults` | `persist-results` | Bedrock (`converse` for grading prose, `invoke_model` for Titan embedding), S3 (put execution report), CloudWatch (custom accuracy metrics via `publish_metrics_to_cloudwatch`), CloudWatch Logs | `event.step_results.collect_metrics`/`execute_migration` | `ExecutionResult`, `Grade`, `MigrationMemory` rows in CockroachDB; `s3://{bucket}/runs/{run_id}/execution_report.json`; four CloudWatch metrics |
| 7 | `Cleanup` | `cleanup` | Secrets Manager (delete shadow secret), CloudWatch (metric on failure only), CloudWatch Logs | `ShadowCluster` row from CockroachDB | `ShadowCluster.status = DESTROYED` in CockroachDB; secret `migration-oracle/shadow/{run_id}` deleted; CockroachDB Cloud cluster destroyed (via provider, not AWS) |
| — | `MarkSucceeded` → `ChooseOutcome` → `WorkflowSucceeded` | (none — `Pass`/`Choice`/`Succeed` states) | none | `$.outcome.workflow_failed` | Execution status `SUCCEEDED`, visible via `describe_execution` |

### Run that fails at ExecuteMigration

1–3 identical to above.
4. `ExecuteMigration` — `run_migration()` (`app/shadow/migration_runner.py`)
   either raises or returns `outcome.success = False` (a real migration
   failure, e.g. a constraint violation) — the handler still returns
   normally (a business-level failure is not a Lambda exception; only an
   unexpected exception triggers ASL `Retry`/`Catch`). `shadow_service.merge_timings`
   still records `migrate_ms` and whatever job-watch data was captured
   before the failure.
5. `CollectMetrics` — runs normally, `success: false` propagates through
   untouched (no AWS calls, pure transform).
6. `PersistResults` — still runs, still calls Bedrock (grading prose
   explains the failure) and still writes a `Grade`/`ExecutionResult`
   row — a failed migration is graded, not skipped.
7. `MarkSucceeded`/`ChooseOutcome`/`WorkflowSucceeded` still apply here,
   because "the migration under test failed" and "the *workflow* failed"
   are different concepts — the ASL only routes to `MarkFailed` when a
   **Lambda itself raises an unhandled exception** (`States.ALL` catch),
   not when the business outcome inside a successful Lambda return is
   `success: false`. `Cleanup` still always runs (via `MarkSucceeded`'s
   unconditional `Next: Cleanup`).

If instead `ExecuteMigration`'s Lambda **raises** (e.g. the shadow secret
was deleted out from under it, or a timeout), the ASL `Catch` fires:
`ResultPath: $.error` → `Next: MarkFailed` → `Cleanup` → `ChooseOutcome`
(now `$.outcome.workflow_failed = true`) → `WorkflowFailed` (a `Fail`
state — the whole Step Functions execution shows status `FAILED` in
`describe_execution`). `Cleanup` still runs identically either way — this
is the entire point of the `MarkSucceeded`/`MarkFailed` → `Cleanup` fan-in
pattern.

## B. Service interaction map

- Control plane **writes** the customer connection secret
  (`_store_connection_url`, `app/api/routes/runs.py`) to Secrets Manager as
  `migration-oracle/connections/{run_id}` → `DiscoverSchemaFunction`
  **reads** it via `event["connection_secret_arn"]` (passed as an ASL
  `Parameters.connection_secret_arn.$: "$.connection_secret_arn"`, itself
  sourced from `WorkflowStartInput.connection_secret_arn` set by
  `WorkflowOrchestrationService.start_for_run`).
- `DiscoverSchemaFunction` **writes** `MigrationRun.schema_snapshot`
  (CockroachDB) and, best-effort, `s3://{bucket}/runs/{run_id}/schema_snapshot.json`
  → `ProvisionShadowClusterFunction` and `LoadSchemaFunction` both **read**
  `MigrationRun.schema_snapshot` back from CockroachDB directly (not from
  S3 — the S3 copy is never read by any downstream step in this codebase).
- `ProvisionShadowClusterFunction` **writes** the shadow cluster's
  connection URL to Secrets Manager as `migration-oracle/shadow/{run_id}`,
  and returns `shadow_secret_arn` in its ASL result → `LoadSchemaFunction`
  and `ExecuteMigrationFunction` both **read** that ARN two ways: first
  preference `event.get("shadow_secret_arn")`, second
  `event["provision_shadow_cluster"]["shadow_secret_arn"]` (via the ASL's
  `Parameters.provision_shadow_cluster.$: "$.step_results.provision_shadow_cluster"`),
  third fallback recomputing `shadow_secret_name(run_id)` locally if
  neither is present — three redundant ways to arrive at the same string,
  never passing the actual credential value through ASL state.
- `ExecuteMigrationFunction` **writes** `ShadowCluster.stage_timings`,
  `schema_snapshot_before/after`, `row_sample_before/after` to CockroachDB,
  and returns a metrics dict in its ASL result → `CollectMetricsFunction`
  **reads** that dict from `event["execute_migration"]` (no CockroachDB or
  AWS read at all — everything it needs arrives in the ASL payload).
- `CollectMetricsFunction` **writes** nothing; its normalized dict becomes
  `$.step_results.collect_metrics` → `PersistResultsFunction` **reads** it
  via `_extract_metrics()`, preferring `step_results.collect_metrics`,
  falling back to `step_results.execute_migration` if collect's output is
  missing/malformed (so `CollectMetrics` is not a hard dependency of
  `PersistResults` — it's a pass-through the persist step can bypass).
- `PersistResultsFunction` **writes** `Grade`/`ExecutionResult`/
  `MigrationMemory` rows (CockroachDB), an S3 execution report, and
  CloudWatch accuracy metrics — none of these are read by any later ASL
  state; they're consumed by the API (`GET /runs/{id}/grade`,
  `/execution-result`, `/memory`) and by the *next, separate* migration
  run's retrieval query, not by anything else in this same execution.
- `CleanupFunction` **reads** the `ShadowCluster` row (for `cluster_id`/
  `cluster_name` to pass to the provider's `destroy()`) and the
  `migration-oracle/shadow/{run_id}` secret (implicitly, via `delete()` —
  it doesn't need the value, just the name) → **writes**
  `ShadowCluster.status = DESTROYED` and deletes the secret. Nothing reads
  from Cleanup's output except the ASL's own `ChooseOutcome` state
  (`$.outcome.workflow_failed`, set earlier by `MarkSucceeded`/`MarkFailed`,
  not by Cleanup itself).
- `run_id` propagation: originates as a CockroachDB `MigrationRun.id`
  (UUID, generated by the API on `POST /runs`), becomes the Step Functions
  **execution name** (`start_execution(name=str(run_id))`, making a
  duplicate start idempotent via `ExecutionAlreadyExists`), becomes
  `$.run_id` in every ASL `Parameters` block, and becomes the deterministic
  suffix of both secret names (`migration-oracle/connections/{run_id}`,
  `migration-oracle/shadow/{run_id}`) and both S3 key prefixes
  (`runs/{run_id}/...`) — the same string is the join key across all four
  services (CockroachDB, Step Functions, Secrets Manager, S3) with no
  translation table anywhere.
- `ShadowSweeperFunction` **reads** `ShadowCluster` rows independently
  (`list_expired_active`) and the shadow provider's own cluster listing
  (`list_app_clusters`, tag-based, CockroachDB Cloud API not AWS) — it has
  no relationship to any specific Step Functions execution or `run_id`; it
  is the one component in this map that doesn't participate in the
  run_id-keyed handoff chain at all.

## C. Things I might misrepresent

- **"Only `PersistResultsFunction` can reach Bedrock" is true only inside
  the Step-Functions-orchestrated path.** The FastAPI control plane
  constructs `AwsBedrockClient`/`AwsTitanEmbeddingClient` directly in at
  least three other places (`app/dependencies.py:183,211`,
  `app/memory/open_source_corpus.py:282`) using its own AWS credentials,
  which this SAM template's IAM policies do not govern at all. A reader
  who takes the IAM table as the complete story about "who can call
  Bedrock in this system" would be wrong.
- **Five of seven S3-permissioned Lambda functions never call S3 in their
  own handler code**: `ProvisionShadowClusterFunction`, `LoadSchemaFunction`,
  `ExecuteMigrationFunction`, `CollectMetricsFunction`, and
  `CleanupFunction` all hold `s3:PutObject`/`GetObject`/`ListBucket` IAM
  grants that are currently unused (confirmed by exhaustive grep for
  `runtime.artifacts` — only `discover_schema.py` and `persist_results.py`
  call it). This is not a bug, but describing S3 as "used by the pipeline"
  without this caveat overstates how load-bearing it actually is.
- **`CollectMetricsFunction` makes zero AWS SDK calls of any kind.** It
  holds S3, Secrets Manager, and CloudWatch IAM grants and uses none of
  them — its entire body is a dict transform over the previous step's ASL
  payload. It exists as a separate Lambda/ASL state for pipeline-shape
  reasons (a distinct named stage in the trace), not because it needs
  distinct AWS permissions.
- **`SecretsService.store_customer_connection()` is dead code.** It reads
  as if it were the customer-secret write path (it has the most complete
  docstring and field mapping of any secret-writing method in the
  codebase), but it has zero call sites. The actual write path is
  `_store_connection_url()` in `app/api/routes/runs.py`, which calls a
  lower-level `put_json` directly and uses a slightly different JSON shape
  (`{"database_url": ...}` vs. `store_customer_connection`'s structured
  `{host, port, database, username, password, ssl_mode}`).
- **`ArtifactStore.put_step_output()`/`step_output_key()` and
  `get_bytes()`/`get_json()` are unused.** The "generic per-step S3
  artifact" mechanism the naming convention implies was built but never
  wired into any handler; only the two specific methods
  (`put_schema_snapshot`, `put_execution_report`) are actually called, and
  nothing in the current codebase ever reads an artifact back from S3.
- **`validate_workflow_definition()` (AWS's own ASL validation API) is
  never called during normal operation** — only from two verification
  scripts. A reader might assume ASL correctness is checked at deploy or
  startup time; it isn't, automatically.
- **`ensure_infrastructure()`/`ensure_standard_alarms()`/
  `ensure_standard_log_groups()` cannot succeed under any of the eight
  Lambda execution roles** — none of them are granted
  `logs:PutRetentionPolicy` or `cloudwatch:PutMetricAlarm`. These only work
  when run by an operator with broader credentials
  (`verify_phase8_full.py`, `verify_phase8d_aws.py`). The alarms
  `docs/HACKATHON_TOOLS.md` references as "orphan alarms" are not
  self-provisioning infrastructure — they require a manual script run with
  elevated permissions relative to what's deployed.
- **Both CloudWatch alarms are created with `ActionsEnabled: False`.**
  They can enter `ALARM` state but there is no SNS topic, email, or webhook
  anywhere in this codebase wired to them — "we have alarms" would be
  misleading without noting they don't notify anyone.
- **`AwsClientFactory.lambda_()` (the boto3 `lambda` client) is dead
  code** — defined, never called. No component in this system invokes a
  Lambda function via the AWS API; the only two invocation mechanisms are
  Step Functions (the deployed path) and a direct in-process Python
  function call (`HANDLERS["cleanup"](...)` in `abort_for_run`, plus
  whatever "local runner" the `app/lambdas/__init__.py` docstring refers
  to, not located/verified in this audit).
- **The `bedrock-runtime` client is not part of `AwsClientFactory` at
  all** — `AwsBedrockClient` and `AwsTitanEmbeddingClient` each construct
  their own boto3 session/client independently, with their own timeout
  configuration, bypassing the shared factory's caching entirely. A reader
  assuming all AWS clients in this codebase flow through one factory (a
  reasonable assumption given the factory's docstring: "Reusable boto3
  clients for AWS services used by Migration Oracle") would be wrong for
  Bedrock specifically.
- **CockroachDB Cloud cluster provisioning/destruction is not an AWS
  service call**, even though it's triggered from inside AWS Lambda
  functions running in `us-east-1`. `provider.create()`/`provider.destroy()`
  (referenced throughout `provision_shadow.py`, `cleanup.py`,
  `sweeper.py`) call the CockroachDB Cloud REST API over HTTPS, authenticated
  by `CCLOUD_API_SECRET` — not a boto3 call, not IAM-governed, not
  covered by any policy block in this template. It would be easy to
  misread "ProvisionShadowClusterFunction has broad Secrets Manager
  permissions" as being about AWS resource provisioning, when the resource
  actually being provisioned (the CockroachDB cluster itself) is entirely
  outside AWS's control plane.
- **`GradingPipelineService`'s CloudWatch call
  (`grading_pipeline_service.py:207-210`) constructs a second, independent
  `AwsClientFactory`/`CloudWatchObservability`** rather than reusing
  `runtime.observability` from the Lambda's shared runtime — functionally
  harmless under the default credential chain, but worth knowing if anyone
  goes looking for "the one CloudWatch client" and only checks
  `LambdaRuntime`.
